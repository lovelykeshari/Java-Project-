# Online Event Management System

A Java 17 / Jakarta Servlet web application for managing event submissions, approvals, attendee registrations, and user accounts. It is designed as a compact academic project that demonstrates requirement analysis, object-oriented design, Java collections and exceptions, background threads, JDBC, transactions, and servlet sessions.

## Requirement analysis

### Users and goals

- **Administrator:** manage user accounts, approve or reject event submissions, and review system activity.
- **Event organizer:** submit events, edit their own pending events, and view registrations for approved events.
- **Attendee:** browse approved events and register once for each event.

### Functional requirements

1. Authenticate users and retain the signed-in identity and role in an HTTP session.
2. Submit event proposals with title, description, venue, date/time, capacity, ticket price, and organizer.
3. Allow an administrator to approve or reject submitted events.
4. List approved events and allow attendees to register subject to capacity and duplicate-registration checks.
5. Let organizers view attendee registrations for their events; let administrators list and manage users.
6. Persist data in a relational database using parameterized JDBC statements.
7. Run a small background reminder worker to demonstrate safe thread lifecycle and collection use. In production, reminders would be dispatched through a durable job queue and delivery service.

### Quality requirements and scope

- Use role checks on server-side endpoints; do not trust a role supplied by a browser form.
- Validate input and report expected failures as readable HTTP responses.
- Use database constraints and transactions to protect capacity and registration integrity.
- This is an educational starter, not a production ticketing/payment system. Passwords are hashed with PBKDF2; there is no payment processing, email delivery, CSRF protection, or production secret management. Add those before real deployment.

## Design

```text
Browser
  -> Servlets + AuthFilter (HTTP, sessions, role checks)
  -> EventService / RegistrationService / UserService (validation and workflows)
  -> Repository interfaces
  -> JDBC repositories + Database (prepared statements, transactions)
  -> H2 database (schema.sql)
```

Domain objects (`User`, `Event`, `Registration`) keep data and behavior together. Services enforce application rules. Repositories isolate SQL. `RegistrationService` reserves a seat and inserts a registration within one transaction. The servlet layer converts HTTP input/output and stores only the authenticated user ID and role in the session.

## Requirements

- JDK 17 or newer
- Maven 3.8+
- Apache Tomcat 10.1 (Jakarta Servlet 6)

## Build and run

1. From this directory, build the WAR:

   ```bash
   mvn clean package
   ```

2. Copy `target/online-event-management.war` into Tomcat 10.1's `webapps` directory and start Tomcat.
3. Open `http://localhost:8080/online-event-management/`.

On first application startup, the H2 database is created at `./data/event-management` relative to Tomcat's working directory, and `schema.sql` initializes its tables. Set `EVENT_DB_URL`, `EVENT_DB_USER`, and `EVENT_DB_PASSWORD` to override the database connection. Ensure the Tomcat process can write to the database directory.

### Demo users

The initializer creates these accounts if they do not already exist. Change the passwords before any shared deployment.

| Role | Email | Password |
| --- | --- | --- |
| Admin | `admin@example.com` | `Admin123!` |
| Organizer | `organizer@example.com` | `Organizer123!` |
| Attendee | `attendee@example.com` | `Attendee123!` |

The login form is available at `/login`. After login, role-appropriate pages are served under `/events`, `/registrations`, and `/admin/users`. Forms use ordinary HTML generated by the servlets; the project contains no JavaScript.

## Endpoint guide

| Method and path | Access | Purpose |
| --- | --- | --- |
| `GET/POST /login` | Public | Sign in and create a session |
| `POST /logout` | Signed in | Invalidate session |
| `GET /events` | Signed in | Browse approved events |
| `POST /events` | Organizer | Submit an event for review |
| `POST /events/decision` | Admin | Approve/reject an event |
| `GET /registrations` | Attendee or organizer | Register for an event or view organizer registrations |
| `GET/POST /admin/users` | Admin | List, create, and delete user accounts |

For ease of review, servlets return simple HTML and status codes directly. The filter protects restricted paths, while services also validate ownership and workflow rules.

## Database model

- `users`: unique email, display name, role, salted PBKDF2 password hash.
- `events`: organizer foreign key, event details, approval status, capacity and ticket price.
- `registrations`: attendee/event foreign keys and a unique `(event_id, attendee_id)` constraint.

`schema.sql` is the canonical schema. SQL is executed with `PreparedStatement`; registration uses a JDBC transaction and row-level locking to prevent overbooking.

## Project structure

```text
src/main/java/com/example/eventmanagement/
  config/        Database and application lifecycle
  model/         User, Event, Registration, Role, EventStatus
  repository/    JDBC repositories and transaction support
  service/       Validation and business workflows
  servlet/       Login, event, registration, admin, logout endpoints
  filter/        Session authentication and role access
  util/          Password hashing, HTML escaping, domain exceptions
src/main/resources/schema.sql
```

## Notes

- H2 is embedded for a zero-configuration demonstration; JDBC repositories can be adapted to PostgreSQL or MySQL by changing the driver and connection URL.
- A daemon reminder worker uses a `BlockingQueue` and `ExecutorService`, and is stopped by the servlet context listener.
- Do not commit real credentials or database files. The local H2 database is created at runtime and is not included in this repository.
